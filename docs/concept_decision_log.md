# コンセプト整理と要件判断メモ

## 目的

このメモは、`self_reward_app`のコンセプトについて出てきた疑問点、議論した論点、設計上の判断ポイント、現時点で採用する要件を整理するためのもの。

特に以下の違和感を起点に整理する。

- 長期的な学習の道標となるアプリなのに、サブゴール配下に毎日のTodoを置くと、短期Todo管理アプリに見えてしまう
- 毎日の学習Todoを作る設計は、サービスの価値検証としてズレているのではないか
- 最初に考えていた「学習時間をゴールドに変換し、ご褒美と交換する」案を入れると、再びご褒美アプリに戻ってしまうのではないか

## 現時点のコンセプト

このサービスは、単なるTodo管理アプリでも、単なる習慣化アプリでも、ご褒美交換アプリでもない。

現時点のコンセプトは以下。

> 自分が目指す未来までの道のりを見える化し、毎日の学習を前進と報酬に変える、長期学習のためのロードマップアプリ。

中心に置く価値は「学習を管理すること」ではなく、以下を見えるようにすること。

- なぜその目標を目指しているのか
- 長期ゴールまでの道のりはどうなっているのか
- 今どのサブゴールに向かっているのか
- サブゴール達成に必要なことは何か
- 日々の学習がどの前進につながっているのか
- 小さな達成を認め、休息やご褒美につなげられるか

## サービス構造

現時点では、以下の階層で考える。

```text
価値観
  └ 長期ゴール
      └ サブゴール
          └ クエスト
              └ 日々の学習
```

各要素の役割は以下。

| 要素 | 役割 |
| --- | --- |
| 価値観 | なぜその目標を目指すのかを思い出すための軸 |
| 長期ゴール | 最終的に到達したい状態 |
| サブゴール | 長期ゴールまでの中継地点 |
| クエスト | サブゴール達成に必要なやることリスト、達成条件 |
| 日々の学習 | クエストを進めるための実際の行動 |
| ご褒美 | 達成や前進を自分で認めるための体験 |

## 論点1: サブゴール配下のリストは毎日のTodoなのか

### 疑問

サブゴールに毎日の活動をTodoとして設定すると、長期的な学習の道標というコンセプトとズレるのではないか。

毎日のTodoを作ると、以下の問題が起きる。

- 日次タスク管理アプリに見える
- Todoを消化することが主目的になる
- 未完了Todoが残ることで焦りや罪悪感が増える
- 既存のTodoアプリや習慣化アプリとの差が弱くなる
- サービスの価値検証が「長期学習の道標」ではなく「Todo管理の便利さ」に寄ってしまう

### 判断

サブゴール配下のリストは、毎日のTodoではなく「クエスト」として扱う。

クエストは、その日に必ずやるタスクではなく、サブゴールを達成するために必要な達成条件である。

例:

```text
長期ゴール:
Webエンジニアに転職する

サブゴール:
Rails基礎を理解する

クエスト:
- MVCの流れを説明できる
- CRUDアプリを1つ作る
- バリデーションを使える
- アソシエーションを理解する
- ログイン機能を実装できる
```

この場合、ユーザーは毎日Todoを作るのではなく、学習を通じてクエストを進め、できるようになったらクエストをクリアする。

## 論点2: 日々の学習はどう扱うか

### 疑問

日々の学習を扱わないと、アプリを継続利用する理由が弱くなる。一方で、日々の学習をTodo化するとコンセプトからズレる。

### 判断

日々の学習は「今日やるTodo」ではなく、「クエストを進めるための行動」として扱う。

ユーザーの動線は以下。

```text
長期ゴールを見る
  -> 今向かうサブゴールを見る
  -> そのサブゴールのクエストを見る
  -> 日々の学習を行う
  -> 進んだクエスト、またはクリアできたクエストをチェックする
```

重要なのは、毎日タスクを追加させることではなく、学習後に「今日はどの前進につながったか」を確認できること。

## 論点3: ゴールドとご褒美をどう扱うか

### 疑問

最初に考えていた「学習時間がゴールドに変換され、ご褒美と交換できる」仕組みは、日々の学習モチベーションとして使えそう。

一方で、それを強く設計すると、サービスが「長期学習のロードマップ」ではなく「学習時間を稼いでご褒美を交換するアプリ」に戻ってしまう。

### 分析

ゴールドとご褒美には、短期的な行動を促す力がある。

ただし、設計上の引力が強く、主役にすると以下の問題が起きる。

- 学習の意味より、学習時間の量が主役になる
- ゴールドを稼ぐために学習する状態になる
- 休むと損した感覚が生まれる
- 完璧主義や焦りを持つユーザーをさらに追い込む可能性がある
- 「長期目標への現在地を見える化する」という価値検証がぼやける

### 判断

現時点の検証では、ゴールド経済は主機能にしない。

代わりに、以下の報酬設計を採用する。

- クエストをクリアしたら、小さなご褒美を選べる
- サブゴールを達成したら、大きなご褒美を受け取れる

これにより、報酬は「学習時間を稼いだ対価」ではなく「意味のある前進を認める体験」として扱える。

## 採用する報酬設計

報酬は2段階に分ける。

```text
長期ゴール
  └ サブゴール
      ├ クエスト
      │   └ クリアしたら小さなご褒美
      └ 全クエストクリア
          └ サブゴール達成、大きなご褒美
```

### クエスト報酬

役割は、日々の前進を認めること。

- 小さな達成感を作る
- 今日の学習を報われた感覚にする
- サブゴールまで遠くても途中で区切りができる
- 毎日のTodoではなく、クエストクリアに紐づくためコンセプトからズレにくい

クエスト報酬は「小さなご褒美」として扱う。

例:

- 好きなドリンクを飲む
- カフェで少し休む
- 30分好きな動画を見る
- 欲しかった小物を買う

### サブゴール報酬

役割は、節目を祝うこと。

- 中継地点に到達した感覚を作る
- 長期学習の道のりを進んだ実感にする
- 「ここまで来たから休んでよい」という納得感を作る

サブゴール報酬は「大きなご褒美」として扱う。

例:

- 半日しっかり休む
- 欲しかった本を買う
- 外食する
- 小旅行に行く

## 現時点の要件

### 1. 長期ゴールを設定できる

ユーザーは、自分が最終的に到達したい長期ゴールを設定できる。

例:

- Webエンジニアに転職する
- 英語で仕事ができるようになる
- ポートフォリオを完成させる

### 2. 価値観を設定できる

ユーザーは、その長期ゴールを目指す理由や大切にしたい価値観を設定できる。

例:

- 自立して生活したい
- 家族やパートナーとの生活を良くしたい
- 好きな場所で働けるようになりたい

### 3. サブゴールを設定できる

ユーザーは、長期ゴールまでの中継地点としてサブゴールを設定できる。

サブゴールは、毎日のTodoのカテゴリではなく、長期ゴールに向かうためのまとまった到達地点として扱う。

例:

- Rails基礎を理解する
- ポートフォリオの主要機能を完成させる
- 応募書類を作成する

### 4. サブゴールごとにクエストを設定できる

ユーザーは、サブゴールを達成するために必要なクエストを設定できる。

クエストは日次Todoではなく、サブゴール達成の条件として扱う。

例:

- CRUDアプリを1つ作る
- バリデーションを使えるようにする
- アソシエーションを説明できる
- ログイン機能を実装する

### 5. クエストをクリアできる

ユーザーは、学習を通じて達成できたクエストをクリアできる。

クエストをクリアすると、小さなご褒美を選べる。

### 6. 小さなご褒美を設定できる

ユーザーは、クエストクリア時に選べる小さなご褒美を設定できる。

小さなご褒美は、日々の前進を認めるためのものとして扱う。

### 7. サブゴール達成で大きなご褒美を受け取れる

サブゴール内の全クエストをクリアしたら、そのサブゴールを達成した状態にする。

サブゴール達成時には、大きなご褒美を受け取れる。

### 8. マップ上で現在地と道のりを確認できる

ユーザーは、長期ゴール、サブゴール、クエストの進み具合をマップ上で確認できる。

目的は、単に進捗率を見せることではなく、自分がどこに向かっていて、どこまで進んだかを直感的に理解できるようにすること。

## MVPで検証したい価値

MVPでは、以下を検証する。

- 長期ゴール、サブゴール、クエストの構造があることで、学習の道のりが見えやすくなるか
- 日々の学習がクエストクリアにつながることで、前進感が生まれるか
- クエストクリア時の小さなご褒美が、学習継続のモチベーションになるか
- サブゴール達成時の大きなご褒美が、節目を祝う体験として機能するか
- Todoアプリよりも心理的に疲れにくいか
- 「今日も少し進んだ」「ここまで来たから休んでよい」と感じられるか

## 現時点でやらないこと

以下は、現時点では主機能にしない。

- 毎日のTodo作成
- 学習時間をゴールドに変換する経済システム
- ゴールド残高の管理
- ご褒美交換所
- 連続学習日数の強い強調
- 未完了タスク数の強い表示
- 他ユーザーとの競争

これらは、長期学習の道標という検証軸をぼかす可能性があるため、後回しにする。

## 用語の見直し

現状の`TodoItem`という名称は、日次Todo管理を想起させる。

今後の設計では、以下のように用語を見直す。

| 現在の表現 | 見直し後の表現 |
| --- | --- |
| TodoItem | Quest |
| Todo | クエスト |
| Todo完了 | クエストクリア |
| 今日やったこと | 学習ログ、または今日の一歩 |
| サブゴール完了 | チェックポイント到達 |
| ご褒美獲得 | ご褒美を選ぶ、受け取る |

## 最終判断

現時点では、以下の設計を採用する。

> サブゴール配下には毎日のTodoではなく、サブゴール達成に必要なクエストを置く。ユーザーは日々の学習を通じてクエストをクリアし、クエストクリア時には小さなご褒美を選べる。全クエストをクリアするとサブゴール達成となり、大きなご褒美を受け取れる。

この設計により、以下を両立する。

- 長期ゴールまでの道のりを見える化する
- サブゴールを中継地点として機能させる
- 日々の学習に短期的な達成感を作る
- ご褒美機能を主役にしすぎず、前進を認める体験として使う
- Todo管理アプリや習慣化アプリとの差を保つ
